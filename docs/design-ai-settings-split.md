# AI settings split

Status: option A approved by the owner on 2026-10-27, built step by step (the queue and the status of each step are in `TASKS.md`). It was reviewed independently by gpt-6-astra the same day; the corrections below come from that review. Evidence is a source-only investigation (GPT, commit `a69d308`); the findings below were rechecked by content where they decide something.

## The problem

Settings > "Models & Agent" (id `ai-providers`) holds connections, three job rows, the search index and proactive help: provider setup, model choice, behaviour and diagnostics on one page. Speech keys and translation sit in the audio tab, answer language and style in General. A user who wants live translation with a cloud model crosses two pages and about 14 controls; proactive help plus live speech crosses two pages and about 17.

## What the product really has

About 30 call sites reduce to seven model settings. The user should see these, not thirty features:

| Model setting | Jobs it serves |
| --- | --- |
| Quick answers | What to say, Clarify, Follow-up, rephrase, Recap, code hint, Brainstorm, screenshot analysis, answers from past meetings (RAG), resume and role analysis, interview prep, live-context compaction |
| Summaries | Meeting notes and the meeting title (live Recap is not here) |
| Agent | The typed agent with tools, and the proactive cards it drafts |
| Proactive decision | Its own System One service (URL, key, model); not a connection |
| Translation | Per-sentence and paragraph translation |
| Search index | Embeddings for meetings, summaries and materials |
| Speech | Eight services (Google Cloud Speech, Deepgram, Soniox, OpenAI, Groq, ElevenLabs, Azure, IBM Watson) with their own credentials |

Transcript second-pass correction needs no model (it merges reopened turns); the intent classifier is a bundled local model; neither needs a picker.

## Proposed structure (option A, "federated")

Tab ids stay, labels change: General, Audio & Translation, **AI functions** (`ai-providers`), **Provider setup** (new id), Shortcuts, Knowledge, About.

- **Provider setup**: the services Pika connects to. The model is the one in quotio's provider list (`../../ops/quotio`, `Views/Components/CustomProviderSheet.swift` and its Custom Providers list): one row per provider the user has added, never a fixed list of companies (owner feedback, 2026-10-27; `electron/services/aiConnections.ts` already says Pika is not tied to any provider and that a connection is a type, a host and a key). Every provider speaks one of three interfaces, so the user picks the **interface**, not a company.
  - Language model providers: one row per configured provider: the name the user typed, the interface ("OpenAI compatible", "Anthropic compatible", "Gemini compatible"), the host, a state in words and a mark (Key saved, No key, Test failed), and a delete button (two presses: the row asks "Delete <name>?" first). Clicking the row opens the editor. Add provider opens the same editor: Interface (three choices, which fills the default Base URL), Name, Base URL, API key, **Custom headers (optional)** with Add header and an empty state, Test, Save, Cancel. OpenAI, Groq, OpenRouter, DeepSeek, a gateway of your own, Ollama and LM Studio are all "OpenAI compatible" and need no row of their own and no preset chip. There is no sample or default name in the product: the list starts with what the user has configured.
  - Speech-to-text providers: the same list pattern (Add provider starts with the service, the fields change with it: a key; a key and a region; a service-account file), one credential slot per service as today. The service being edited is separate from the service that transcribes. Audio & Translation lists only the services set up here and shows a setup state when there are none. This is a behaviour change, not a move: today `audio-pipeline.ts` substitutes Google when the selected service has no key, and OpenAI has model alternatives; S3b must decide and test that routing, S3a only moves the controls.
  - Decision service (proactive help): base URL, key, Remove key, Save, and a Test of the configured endpoint. A separate kind of service, not a language model provider. Proactive help's current Save writes the URL and key together with mode, model, threshold and cooldown; after the split each page saves only its own fields (the existing `agent-gate-set-settings` accepts partial fields) and a stale page must not overwrite the other.
  - The four built-in records (`gemini`, `openai`, `claude`, `groq`) are synthesized by `CredentialsManager`, are referenced by id from saved settings (`chatConnectionId`, `summaryConnectionId`, `agentConnectionId`, `embeddingConnectionId`, `transcriptTranslationProvider`) and cannot be deleted or renamed by the storage API. Showing only the configured ones therefore has consequences the review found: a job that still names a built-in with no key keeps failing with a setup error (Summaries and Agent do not inherit from an explicit id; translation is skipped; embeddings probe and may fall to the local model), the job pickers currently list all four built-ins, and an unlisted built-in has no editor. **Proposed policy for S1b, pending the owner**: the list shows configured built-ins plus every custom provider; the job pickers list only configured providers plus the one a job currently names (so a saved choice never disappears), with a link to the editor for it; a built-in's name and interface are read-only, its key and host stay editable, and its row action is "Remove key and reset host", not Delete; a custom provider cannot be deleted while a job names it (the row says which); nothing ever clears or reassigns a job on its own. Add always creates a custom provider with a new id, and it may duplicate the service of a configured built-in; rows are told apart by host and interface, never merged by name.
  - **Custom headers are new and are an end-to-end change** (the review found it larger than a three-client tweak). One optional `headers` map inside each custom provider record (`openaiCompatibleProviders`), kept in the main process; built-ins get none. Every place that builds a request from a connection must send them: the three SDK clients in `LLMHelper`, the three model-list requests in `connectionModels.ts`, the three pi-ai model registrations in `electron/agent/models.ts` (pi-ai 1.4.0 supports a model `headers` field for all three protocols, confirmed in its installed source), and the embedding provider's shared fetch in `ConnectionEmbeddingProvider.ts`. Two hand-built projections would still drop them and must carry them: the model-list input in `electron/ipc/connections.ts` and the translation connection in `transcript-assembler.ts`. Credential read and write in `CredentialsManager` must resolve headers and keep them across unrelated edits. Header values are secrets: write-only (the renderer gets names and a "set" mark only; edits send explicit keep, set or remove; blank never erases), validated (HTTP token names, no CR, LF or control characters, no duplicates ignoring case, size limits), never logged, and redacted from every error that reaches the renderer or a log (today only the API key is redacted in `modelTest.ts`; `agentTest.ts` and the meeting summary log redact nothing). They are stored in the same plaintext `credentials.json` as the keys until the encryption task lands. A selected embedding provider must be rebuilt after its connection's headers or host change. Headers do not apply to speech, the decision service, Tavily or Automatic embeddings, which do not use connections. S5 is therefore two steps: S5a, a dormant backend (storage, validation, every sink above, redaction, tests; no editor), then S5b, the editor.
  No thresholds, languages, prompts, folders or model choices here.
- **AI functions**: one row per model setting that is not about audio: Quick answers (connection, model, Fetch, Save, collapsed Test, a line naming every job it serves, answer language, collapsed answer style), Summaries, Agent (image checkbox, workspace folder), Proactive help (mode, decision model, a read-only line saying cards use the Agent model, collapsed threshold, cooldown and decision log), Search index (Automatic or own, status always visible, collapsed rebuild).
- **Audio & Translation**: devices, speech (service and model, languages), translation (enabled, target, connection and model, Test; source, display, prompt and segmentation under Advanced). Keys and accounts are links to Provider setup.
- **Knowledge** is being rethought, not kept as a resume page: Pika also has to search everyday meetings and the user's materials, not only a resume. See `docs/design-knowledge.md`. The Search index setting moves there, so AI functions has four rows (Quick answers, Summaries, Agent, Proactive help).

Rejected, option B: one "AI functions" page with all the rows, including speech and translation. It rebuilds the overloaded page and separates devices from recognition.

## What is a pure move and what is not

Moving components, headings and links (S1a, S2, the first part of S3 and S4, S6) changes no persisted key and no IPC channel. These steps are not pure moves and change stored data or payloads, each with the owner's approval already given or still needed: S5 (a new optional field on a custom provider record and extended save, list and test payload types), K4 (new settings keys for the Use when answering switches), K5 (a `material` document type, provenance columns, source-list IPC). Also not part of the split, separate tasks listed in `TASKS.md`: automatic model alternatives for embeddings and speech, the Groq model reset when the language changes, the proactive decision Test deadline (5 s test, 2 s live), the Agent Test using saved settings when the draft is incomplete, deleting an Agent connection making it inherit Quick answers, template answers for interview prep and a made-up company rating (against "never invent data"), the missing Watson region input, the Tavily key without an input, and Save and Delete reporting success when the disk write failed (`CredentialsManager` swallows write errors, so a UI test cannot prove a durable Save).

## Steps

The ordered queue is in `TASKS.md` (S1a, S1b, S2, S3a, S3b, S4, S5a, S5b, S6). Each step is one branch and one PR; S1a and S2 to S4 are small relocations, S1b, S3b and S5 change behaviour or data and are briefed separately.

Design rules for every step: base-family tokens only (`DESIGN.md`), no spinners, state as words plus a dot or glyph, at most one filled control, 11/12/14 px, results and errors show the real text, both themes.
